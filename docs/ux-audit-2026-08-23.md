# Dadabase desktop UX audit — 2026-08-23

## Scope

Desktop-first review of the running app. Saved connections were treated as read-only: no remote test, SQL execution, import, DDL, or row changes were performed. The project E2E fixture was used to inspect the data browser, filters, row editor, and join picker without saving a change.

## Findings

### P0: trust, safety, and broken navigation

- The header action labelled **Settings** opens the AI assistant drawer. Fix the route/action mapping and cover it with E2E.
- Workspace state is encoded into a huge opaque URL payload. It is not practical to read, share, debug, or navigate through browser history. Keep only meaningful route parameters in the URL; persist transient panel/layout state locally.
- SQLite onboarding does not expose the same read-only protection shown for Postgres and libSQL. Every connection type needs one consistent safe-mode contract.
- The SQL history exposes raw queries without an obvious retention policy, redaction, or opt-out. Queries can contain sensitive predicate values.
- Write-capable and destructive schema actions sit beside normal browse controls. The current connection, table, and safe/write state need to be visible at the point of action.

### Information architecture and layout

- The home screen has excessive dead space while connection discovery is weak: no search, favorites, last-used state, tags, health, latency, or prominent read-only state.
- Local endpoint paths are displayed in full, which is noisy and can disclose filesystem details in screenshots.
- The Add Connection card is too narrow for a dense, accordion-heavy form. URL import needs a parsed preview, masked secret handling, and a clear before-save safety summary.
- The connection switcher does not provide enough context to distinguish similarly named connections safely.
- Table selection appears both in the sidebar and in the central empty state. Choose a durable primary navigator.
- The Query Logger reserves vertical space while empty and obscures too much content when expanded. Its colored counters have no text legend.
- Saved queries and history are hard to discover and do not form a useful library: no search, names, folders/tags, result metadata, or clear open-versus-rerun behaviour.
- The table toolbar mixes viewing, querying, editing, importing, schema change, joining, and export in a single flat row. Group by intent and move hazardous operations to a deliberate Change menu.
- Disabled actions do not say whether the reason is loading, read-only mode, no primary key, or unsupported capability.
- The generic natural-language hint (`age > 25`) is misleading on arbitrary tables.

### SQL and data workflows

- Custom SQL correctly no longer requires a selected table, but the editor can render bright white inside the dark workspace and leaves redundant blank space below it.
- SQL toolbar actions are mostly icon-only. Add accessible names, tooltips, and a compact shortcut reference.
- Generic snippets such as `SELECT * FROM` are incomplete in a table-independent workspace. Provide useful templates with placeholders and a schema-aware picker.
- The filter builder works, but adding an empty condition immediately creates noisy state. Make its draft state local until it is complete or explicitly applied.
- The Add Row form/JSON split and generated SQL preview are strong. JSON mode should start from a validated schema-shaped object rather than an empty editor.
- The join picker identifies foreign-key paths, but does not yet explain join type, cardinality, selected fields, preview, or resulting SQL.

### Schema visualization and accessibility

- The ER diagram currently shows empty table cards and low-contrast, ambiguous relationship lines. It needs visible columns, PK/FK/type cues, labels, zoom, fit, search, minimap, and auto-layout.
- The Structure view is clear and useful; preserve its type/key/default presentation.
- Many important controls are icon-only or have no accessible name in the accessibility tree, including header, SQL, ER, and status controls.
- Small grey copy and inconsistent theme treatment reduce legibility in the dark workspace.

## What to preserve

- Rows / Structure / ER are the right top-level table modes.
- The data grid has a strong base: inline references, relation expansion, filters, sorting, columns, pagination, export, and zen mode.
- Form and JSON row editing plus generated SQL preview make mutations understandable.
- Table-independent Custom SQL is the correct product direction.
- Timed query logging with table context is useful once it becomes calmer and privacy-aware.

## Delivery order

1. Fix route/action correctness, safe mode, URL state, and accessibility labels.
2. Recompose connection onboarding, home/switcher discovery, and desktop workspace hierarchy.
3. Rebuild the SQL workspace and query library around trustworthy execution and privacy-aware history.
4. Make ER diagrams genuinely useful and add schema snapshots/diff/export.
5. Add DuckDB plus file-oriented analysis after the core workbench is dependable.

## Required E2E journeys

- Settings opens Settings, not AI.
- SQLite, libSQL, and Postgres expose the same safe-mode contract.
- A concise deep link restores semantic table/view/filter state.
- Custom SQL is table-independent, theme-correct, keyboard-operable, and blocked from writes while locked.
- Row changes, import, DDL, and destructive actions state connection/table scope and require an appropriate confirmation.
- Query retention/redaction and saved-query open-versus-rerun flows work.
- ER navigation, labels, layout controls, and export work against the fixture.
- Connection parsing, malformed URLs, failed tests, duplicate names, and read-only persistence are covered.
